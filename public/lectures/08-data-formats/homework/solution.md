## Цель эксперимента

Сравнить производительность, потребление памяти и эффективность сжатия трёх форматов:

- CSV (потоковая обработка);
- JSON (`JSON.parse`, полная загрузка);
- MessagePack (потоковая обработка).

### Характеристики исходных файлов

| Параметр | CSV | JSON | MessagePack |
|---|---:|---:|---:|
| Размер файла | 16.17 MB | 38.87 MB | 12.07 MB |
| Количество записей | 200 000 | 200 000 | 200 000 |

Вывод:

- JSON без сжатия заметно больше CSV (примерно в 2.4 раза).
- MessagePack — самый компактный в raw-виде.
- Причина: JSON хранит имена полей в каждой записи, CSV хранит только значения, MessagePack использует бинарное представление.

### Производительность парсинга

| Показатель | CSV (stream) | JSON.parse | MessagePack (stream) |
|---|---:|---:|---:|
| Время до первой записи | ~1.17 ms | ~150.88 ms | ~3.24 ms |
| Общее время | ~60.59 ms | ~150.88 ms | ~55.44 ms |
| Пиковая память (heap) | ~8.33 MB | ~83.87 MB | ~17.78 MB |

Выводы:

1. CSV и MessagePack заметно быстрее JSON на этом наборе.
2. CSV и MessagePack дают низкую latency до первой записи.
3. JSON не потоковый в формате массива, поэтому первая запись доступна только после полного чтения и парсинга.
4. CSV выигрывает по памяти, так как при стрим-обработке не создаёт большой массив объектов.
5. MessagePack стримится, но всё равно создаёт JS-объекты на записи.

### Влияние реализации CSV-парсера

Отдельное наблюдение:

- regex-парсер CSV: `~455 ms` (первый запуск);
- упрощённый `line.split(separator)`: `~60–68 ms` (последующие запуски).

Вывод:

- производительность CSV-сценария сильно зависит от реализации парсера, а не только от формата.

Что делает регулярка из варианта со звёздочкой:

- `(?<!\\\\)${sep}` — ищет разделитель, перед которым нет обратного слеша (то есть не `\,`);
- `(?=(?:[^"]*"[^"]*")*[^"]*$)` — проверяет, что справа до конца строки чётное число кавычек, то есть разделитель находится вне quoted-поля;
- затем `.map(...)`:
  - снимает внешние кавычки у поля;
  - превращает `""` во внутреннюю кавычку `"`;
  - возвращает экранированный разделитель `\,` обратно в обычный `,`.

Почему медленнее:

- на каждом поле и строке выполняется несколько regex-проходов с lookbehind/lookahead;
- такие проверки дороже, чем простой `split`, особенно на большом количестве строк.

### Эффективность сжатия

| Формат | Raw | Gzip | Brotli | Zip |
|---|---:|---:|---:|---:|
| CSV | 16.17 MB | 5.58 MB | 3.99 MB | 5.47 MB |
| JSON | 38.87 MB | 6.29 MB | 4.31 MB | 6.29 MB |
| MessagePack | 12.07 MB | 5.43 MB | 4.16 MB | 5.43 MB |

Выводы:

1. JSON очень хорошо сжимается из-за повторяющихся ключей.
2. После сжатия разница между форматами становится существенно меньше.
3. Преимущество MessagePack в raw-виде уменьшается после gzip/brotli.

### Потоковая обработка по форматам

- CSV: потоковая обработка естественна (построчное чтение).
- JSON: классический JSON-массив не потоковый для `JSON.parse`.
- MessagePack: потоковый режим возможен через `PackrStream`/`UnpackrStream` (библиотечный механизм).

### Итог

1. CSV — лучший для плоских табличных данных и стрим-обработки с минимальной latency/памятью.
2. JSON — самый удобный для разработки и API, но тяжелее по raw-размеру и стартовой latency.
3. MessagePack — хороший компромисс для сложных структур: компактный raw-формат и быстрый потоковый decode.

Практический выбор:

- плоские записи и максимальная streaming-эффективность: CSV;
- сложные структуры и экосистема API: JSON;
- сложные структуры + упор на throughput/compactness: MessagePack.
